4.2 Agent Factory：草案到可治理发布

Factory 把场景经验变成可测试、可回滚、可追溯的 Agent 资产；“能运行”只是起点。

建议的构建链

01

场景草案

从业务目标、流程断点、输入与输出开始，先写清成功和失败边界。

02

Group Agent

按任务拆分子 Agent；确定谁编排、谁调用、谁在异常时交人。

03

能力与边界

接入 Ontology / Data / Model / Skill / MCP / Tools，配置权限、上下文和 Action。

04

沙盒与发布

Qualification 通过后版本发布；记录调用、Token、错误、人工介入和业务反馈。

谁在何处负责判断

  • DT：业务数字化、流程和数据关系；确认系统接口与流程口径。
  • FDE：现场交付与领域知识；补充异常、例外和真实操作边界。
  • Senior User：判断结果是否可用；参与规则、输出和接管设计。
  • Developer：Connector、Tools、部署、日志和工程实现。
  • 业务 Owner / IT Security：价值指标、权限、安全与生产要求待确认。

角色不是固定组织架构；本页用于现场补齐 Owner、输入、产出和决策门。

构建原则

每一项能力都要留下证据。 草案要能回到场景；配置要能解释权限；测试要能重现异常；发布要能定位版本。现有 Agent Factory 是否已覆盖这些环节，需以实际环境逐项核验。

从“搭出来”转成“可治理资产”

阶段必须回答现场产出
构建输入从哪里来？哪个 Ontology 对象承接？场景卡、能力目录、Action 清单
Qualification缺失数据、错误规则、权限越界如何处理？测试集、预期输出、失败证据与 Owner

1.2 从系统字段到统一业务上下文

Ontology 让对象和关系可解释；Data Hub 让事实带着来源、时间与责任进入流程。

Ontology Studio · 对象关系，不是字段清单
主体
Customer承诺对象与服务关系
交易
Order / Back Order需求、缺料与状态
资源
Part / Inventory可用量与替换约束
执行
Repair / Shipment维修节点与运输状态
判断
ETA / Priority风险、优先级与解释
结果
Service Promise / Action承诺与可执行动作

关系示例：缺料影响维修与 Service Promise；库存和运输状态改变 ETA；Priority 影响替换与分配规则。具体对象范围待业务 Owner 确认。

Data Hub · 事实需要可追溯
客户与订单CRM / Order：请求、承诺、状态
执行与资源维修、Field Service、库存、物料、物流节点
知识与规则UKM / EKP / EKF、SOP、PRD、历史案例
上下文标记来源系统、更新时间、Owner、脱敏与权限

冲突如何处理

同一 Order 在不同系统状态不一致时，不静默覆盖；保留来源与时间，标记冲突，交给规则或人工确认。

过期如何暴露

ETA、库存和知识都需要新鲜度口径。过期不是“没有数据”，而是进入判断前的风险信号。

工作坊推演

选一个 BO 情境，逐项填写对象、关系、事实源、更新时间、Owner 与缺失后的替代路径；不声称已实现接入。
